### Image Viewer

Displays JPEG, PNG, GIF, BMP, WebP, TIFF, HEIC, HEIF, AVIF, and JPEG XL images. EXIF metadata (camera make/model, GPS coordinates, timestamp, ISO, aperture) is shown in the Properties panel when available. A PNG's `tEXt` chunks (free keyword/text pairs such as `Creation Time`, `Author`, `Comment`, `Software`) are shown under **PNG text**, every one as stored and in stored order; the PNG `eXIf`, `zTXt` and `iTXt` chunks are not read yet, and the EXIF row says so.

**C2PA (Content Credentials) detection**, for every image format above where the C2PA spec actually defines an embedding (matching EXIF's format breadth): JPEG (APP11 segments), PNG (`caBX` chunk), GIF (Application Extension block), WebP (RIFF `C2PA` chunk), TIFF and BigTIFF (tag `0xCD41`, in any IFD of the main chain), HEIC/HEIF/AVIF (BMFF `uuid` box), and box-form JPEG XL (top-level JUMBF superbox). The same detection runs for audio and video files, see the [Media Viewer](media-viewer.md). If a manifest is found, the Properties panel shows the generator software, the claimed actions and their software agent(s) (edits/operations recorded against the asset, and which tool performed each one), the IPTC Digital Source Type when present — shown as its official IPTC name plus code, e.g. "Created using Generative AI (trainedAlgorithmicMedia)", the actual "AI-generated" signal C2PA carries — ingredients (prior assets this one was derived from, i.e. the provenance chain), and the claim signature's leaf certificate identity (Signed By / Cert Issuer / Cert Valid). This is **structure parsing only** — the certificate is read, not cryptographically verified against a trust store, and revocation is never checked; the `C2PA Signature` row says so explicitly. The `C2PA` row always appears, never silently omitted: "Not present" for a supported format whose structure was read to its end without C2PA data, "Not defined by the C2PA spec for this format" for BMP, ATX/KTX texture archives, and a bare (box-less) JPEG XL codestream — the spec genuinely has no embedding mechanism for any of these — and "Not checked" for a file whose container isn't recognised by its content. When the structure ends early (a box, chunk or segment runs past the end of the data or has an invalid size), the row names the offset where the scan stopped instead of "Not present". C2PA data that is found but not evaluated — a C2PA box or chunk that holds no JUMBF superbox, a Brotli-compressed JUMBF box in JPEG XL, an unknown block version or field type — is listed with its offset under `C2PA scan notes`. A file holding more than one Manifest Store gets a `C2PA` row naming them by offset, and each store's rows are numbered (`C2PA #1 Actions`, `C2PA #2 Actions`).

**XMP Digital Source Type** is a second, independent AI-provenance signal, shown alongside C2PA when present: some tools (Google/Gemini among others) embed the IPTC Digital Source Type directly in XMP without a full C2PA manifest at all. Detection is container-agnostic — it searches for a self-delimited XMP packet anywhere in the file's bytes, so it works the same way regardless of which image format embeds it. Shown as `XMP Digital Source Type` plus, when present, `XMP Creator Tool`, `XMP Creator(s)`, `XMP Credit`, and `XMP Rights`.

> **Forensic note — HEIC/HEIF:** Common on iOS devices (default since iOS 11). A file labelled `HEIC` in the filesystem panel is identified by its ISOBMFF `ftyp` container brand — not by its extension. A `.mp4` or `.jpeg` file can be a HEIC container; Crush will detect and display it correctly regardless. Use `type:heic` in the filter field to find all HEIC files across an acquisition, including any with misleading extensions.
>
> **Current limitation:** HEIC/HEIF is a container format and can hold multiple images in a single file — burst frames, HDR primary + gain map, depth maps, and Live Photo previews. Crush currently displays only the primary image. Embedded secondary images (depth maps, HDR layers, burst frames) are not yet accessible.
>
> **Forensic note — AVIF:** Used by social media platforms (Netflix, YouTube, Discord) and increasingly on Android and modern browsers. AVIF files downloaded from social platforms frequently have EXIF metadata stripped server-side — the absence of GPS or device metadata in an AVIF is therefore a provenance indicator rather than a sign of camera origin. Like HEIC, AVIF is detected from the ISOBMFF `ftyp` brand (`avif` or `avis`), so `type:avif` finds AVIF content regardless of file extension.
