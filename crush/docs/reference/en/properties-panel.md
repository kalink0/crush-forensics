## Properties Panel

The right panel updates whenever you select or open a file. It shows:

- **File name and path**
- **MACB timestamps** — Modified, Accessed, Changed, Birth. A time the source doesn't store is shown as **—**; a folder that only exists as part of its members' paths in an archive has no time. A stored time of 0 is shown as the time it is, `1970-01-01 00:00:00 UTC`, except where the format defines 0 as no time: a gzip header's MTIME of 0 shows **—** and says so, and on a disk image the reader gives 0 for no time on NTFS, ReFS, F2FS, APFS and HFS+ (and always on FAT/exFAT, whose entries store a reading instead), so a 0 there shows **—**. On every other filesystem (ext2/3/4, XFS, Btrfs, QNX, the flash filesystems …) a 0 is the stored time and shows as 1970-01-01. Times are shown to the whole second: where a source stores a finer resolution (nanoseconds on ext4, APFS and Btrfs and for files on the analysis machine, 100-nanosecond units in NTFS and in a ZIP's NTFS extra field), the fraction is not shown, and the source's own bytes hold it. Each kind is one row: every value of it is shown with its zone (`UTC`, or **as stored, no time zone**), and below it, in small grey text, where it is stored and anything else to know about it. Where a source stores times in several places, every one is shown with where it comes from:
  - **ZIP** — the DOS date/time and the times in the extra fields (Info-ZIP extended timestamp `0x5455`, Info-ZIP Unix `0x5855`, NTFS `0x000a`, PKWARE Unix `0x000d`), from the central directory and the member's local header. A DOS date/time has no time zone: it is shown **as stored, no time zone** and never converted, so it reads the same on every analysis machine; one that is not a valid date shows its stored values and says so. The extra fields hold UTC times.
  - **FAT/exFAT** in a disk image — the directory entry's date/time as stored, with no time zone (FAT stores the last access as a date only); exFAT's stored UTC offset is shown and not applied.
  - **ext2/3/4, APFS, HFS+ and Btrfs** in a disk image — Modified, Accessed, Changed and Birth from the entry's inode (HFS+: its catalog record, which also stores a **Backup** date, shown where it is set), read when the entry is selected. A time the record doesn't hold (e.g. Birth on an ext inode too small for it) shows **—**. APFS has no value for "no time", so a stored 0 shows as 1970-01-01 here, while the Filesystem panel's Modified column shows **—** for it; HFS+ stores 0 for no time, which shows **—** in both. Other filesystems show the Modified time only.
- **Entry status** — what the entry's name and bytes don't show, for every source type: a **symbolic link** (shown with its target, whose text is the entry's content; links are never followed, so a link to a parent folder can't loop and a broken link doesn't stop a folder from opening), a **hard link**, a **special file** (device, FIFO — never read), one of **several entries stored under the same name** in an archive (each is shown — `name`, `name (2)` … in archive order — with its own content), a folder that **could not be listed**, or an iTunes-backup entry with **no content stored** in the backup
- **Container Identifier** — for an iOS container folder (one that directly holds a `.com.apple.mobile_container_manager.metadata.plist`): the identifier of its owner from that plist (`MCMMetadataIdentifier`: an app's bundle identifier, an app group's, an extension's or a system service's). Where there is none, the row says why: the plist can't be read, isn't a valid plist, holds no `MCMMetadataIdentifier` string, or is larger than the 1 MiB read for it (a metadata plist is a few hundred bytes). Shown whatever **View → Show iOS Container Identifiers** is set to
- **Compute Hash…** — button beside **Open Format Info…**, for every entry: the same choice as the Filesystem panel's **Compute Hash** submenu
- **MD5 / SHA-1 / SHA-256 (computed)** — each hash computed for the file in this window (by **Compute Hash**, or the SHA-256 of [integrity mode](integrity-mode.md) on open, extraction or export), labelled *computed* to set it apart from hashes a source stores itself. They stay until the source is closed or read again, or the window is closed; nothing is written to disk. Every computation reads the file again; if a later one gives a different value (the content read changed, e.g. a file on a live disk), both values are shown with a warning. An entry whose entry status says no content is read or stored shows no computed hash
- **Format** — identified format name from the knowledge base (e.g. "SQLite Database", "Android Binary XML"), matched against the file's first bytes as far in as the farthest signature in the knowledge base (64 KiB). The **Type** the Filesystem panel indexes in the background for every file uses the first 2,048 bytes only; formats known by a signature past that — ISO 9660 (byte 32,769), Btrfs (65,600), QNX6 (8,192), LUKS2's second header (16,384), Volume Shadow Copy (7,680), GPT on 4,096-byte-sector disks, an Android super partition, an Apple Partition Map on 2,048-byte-block media — are identified only here, for the selected file.
- **Forensic relevance** — what kind of data this format typically contains
- **Platforms** — which platforms this format originates from
- **Reference** — link to the format specification
- **Parser-specific metadata** — EXIF fields, page counts, parse errors, etc.
- **SQLite blob provenance** — a cell opened via the Table Viewer's **Open as new tab** additionally shows the source table (or the full, untruncated SQL query text if it came from an ad-hoc query), column, row, originating database file, and the chosen display format

The panel refreshes automatically whenever you switch between already-open viewer tabs, not just when a new one is opened.
